# Paid pilot conversion audit and implementation

Audit date: 2026-10-08. This record evaluates the current working tree, including the owner's existing unpublished page/form edits. No production conversion baseline was provided; improvements are hypotheses until measured after deployment.

## Initial inventory

- `/pilot` is a dynamic server route backed by the published Sanity `paid-pilot` resource, package specifications, and resolved offer variant. Static public SEO metadata uses `marketingMetadata`; `/pilot` is sitemap-listed and legacy URLs redirect. The page server-renders its client component, has one H1, and preserves site-level JSON-LD. Its hero's two actions precede six explanatory sections before the application.
- Public headline/description come from Sanity. Hardcoded CTAs say “Start a pilot”, although the action opens a free application; form copy describes “onboarding” before approval/payment. Several section headings and success claims are generic or overstated.
- The five mounted application stages are eligibility, scope, success, approval, and confirmation. Identity, workflow, tools, timing, approval path, owner, diagnosis, and baseline can be inherited. V4 skips legacy discovery. Timing/approval remain editable, but known acquisition questions are repeated, contributor mapping loses range accuracy, later/unknown timing defaults can be incorrect, and an expanded metric checklist replaces the concrete primary test.
- `assessment-definition.ts` defines v4 fields/branches; `assessment-diagnostic.ts` scores 70 operational/30 commercial points and gates High/Mid/Low. Legacy scoring remains in `scoring.ts`. Profile context uses an opaque cookie or authenticated application user's profile. Pilot answers currently accept client diagnostic values and update qualification; this can alter the assessment record rather than record a separate pilot override.
- `/api/leads` validates, persists encrypted submissions, uses idempotency and durable notification/CRM/analytics outboxes, creates customer account/membership and a pilot room, and issues an immediate magic-link credential. The current client and server assign the applicant's email to the production owner even when a different owner is specified.
- Rooms use scoped application memberships, encrypted collaborative drafts, term revisions/conflicts, explicit exception review, reviewer approval, clickwrap acceptance, and payment verification. Prices/offer snapshots are constructed server-side and preserved across room changes. Reuse this infrastructure.
- Account and legacy pilot rooms require authenticated access and robots.txt excludes them, but explicit no-index page metadata is missing. Public metadata must stay independent of private answers.
- Mixpanel is consent-gated; verified submissions deduplicate using submission/event IDs. Existing room UI emits `pilot_approved` on scope confirmation instead of agreement acceptance. Application start is emitted on mount and the client duplicates the server's `pilot_requested` event. Page/stage/validation/drop-off observability can improve without collecting free text.
- Baseline lead suite: 269/270 pass. The existing assessment UI uses an accessible Radix progress bar; one test still queries a native `progress` element. No dedicated frontend lint script exists.

## Implemented decisions

- **Improved:** one compact production-outcome hero, one prominent planning CTA, the form immediately after the offer, and explicit free-plan → agreement → payment language. Published offer price/duration/credit/deadline now agree across hero, form, FAQ, and server proposal. Annual deployment labels show annual totals. Existing styling, limited scope, responsibilities, and technical first-value milestone remain.
- **Improved:** shared mapping carries all applicable v4 diagnostic evidence and legacy answers, while explicit pilot fields remain editable. The server retains the original assessment, source submission/time, exact contributor range, and qualification. Unknown timing does not imply readiness; contributor count is distinct from participants.
- **Removed:** repeat acquisition questions for assessed applicants, mandatory success checklist/essay, mount-time application starts, duplicate client submission conversions, and premature `pilot_approved` on scope confirmation.
- **Improved:** optional success adjustment, persistent cleared/unchecked overrides, scoped draft/confirmation state, refreshed untouched defaults after a new assessment, stage/error focus, accessible select labels, and accurate production-owner identity.
- **Improved:** existing-email resume requires its authorized session/verification; typed email cannot issue room access. Unsigned provider spoofing is rejected. Submission replay uses persisted input; locks serialize concurrent intake/room creation and recover interrupted linkage. The lock pool adds at most two connections per process and needs production connection-budget review.
- **Improved:** owner room edits cannot overwrite assessment evidence or erase founder qualification. Signature records finalized scope; manual payment marking is local dry-run only. Existing reviewer authorization, conflicts, revision hashes, clickwrap, Stripe checkout/webhooks, payment gating, and launch state remain.
- **Improved:** public metadata/canonical/schema stay public; email-prefilled and authorized personalized states plus account/auth/legacy-room layouts explicitly noindex. This supplements authorization and robots exclusions.
- **Deferred:** schema migrations, additional CRM fields, provider replacement, scoring changes, pricing experiments, new questionnaires, and live performance/conversion claims. None is necessary to make this implementation coherent.
