# @portalshq/analytics

Privacy-conscious analytics contracts, a browser recorder, a Segment delivery adapter, committed-event mappers, and a durable connector that delivers billing and interaction outbox records to a configured sink independently of the owning business packages. Monetization and interaction-orchestrator do not import this package and never call vendors from their transaction paths; analytics reads their committed records and never changes their acknowledgments. The channels app integrates local follow and clipboard actions. Login and authenticated browser identity are not wired in this repository. No Segment, GA4 or BigQuery accounts are configured by this repository.

## Independent delivery connector

`AnalyticsConnector` (`@portalshq/analytics/connector`) is the automatic path. It creates and owns `portals_analytics_delivery`, `portals_analytics_discovery`, and `portals_analytics_migrations` in the application database through versioned, idempotent migrations that are safe to restart and to run concurrently. On start it validates the required source relations and columns (`monetization_outbox`, and `interaction_outbox` when interaction is enabled) and fails with a clear configuration error when a source migration is absent.

Discovery is bounded: per source kind it scans `created_at >= GREATEST(ANALYTICS_START_AT, watermark - discoveryOverlap)` for ledger rows not yet introduced, advancing a per-destination watermark. Only records inserted at or after the required UTC `ANALYTICS_START_AT` cutoff are ever introduced; earlier history needs the explicit backfill command below. The overlap rescan catches transactions that commit late; records committed with an insertion time older than `watermark - discoveryOverlapMs` require the same operator path. Source rows are never updated and `delivered_at`/`published_at` acknowledgments are never read as analytics checkpoints.

Delivery claims rows in short `FOR UPDATE SKIP LOCKED` transactions with an expiring lease sized to cover the claimed batch's serial sends (`claimLeaseMs >= claimBatchSize * requestTimeoutMs`), releases claims early when the remaining lease cannot cover another send, and recovers expired claims after worker termination — concurrent instances share work safely. Each event keeps a stable namespaced ID `portals-analytics:<appId>:<tenantId>:<kind>:<sourceId>` (the Segment `messageId` and `portals_event_id`), plus `portals_source_id` and `portals_source_kind` for warehouse reconciliation. Delivery is at least once: a crash after sink acceptance but before the ledger update can resend, so analytical views must deduplicate by source identity.

Outcomes are classified: sink acceptance → `delivered`; unsupported event types → `excluded`; network, timeout, 429 and 5xx → retryable (`pending` with capped backoff, `dead` after `maxAttempts`); missing verified identity or unauthorized attribution → `blocked`; malformed records, missing source rows and permanent sink rejections → `dead`. Only the failure category is persisted — never record contents or vendor responses. `status()` reports running/ready state, per-source availability, last successful drain, per-state counts, oldest pending age, and last failure category. `retry(kind, sourceId)` and `retryEligible(kind?)` reset only `blocked`/`dead` records — never delivered or excluded ones. Optional error callbacks cannot interrupt ledger updates.

Host lifecycle API: `new AnalyticsConnector({db, sink, destination, appId, startAt, authorizeTenant, resolveWorld?, resolveInteractionIdentity?, ...})`, `start()`, `stop()` (graceful, awaits the in-flight drain), `drainOnce()` for one bounded pass, `migrate()`, `status()`, `retry`/`retryEligible`. The `db` accepts an injected PostgreSQL-compatible pool.

## `portals-analytics` command

`npm exec portals-analytics` (or the package `bin`) runs a supervised connector. Required environment:

- `ANALYTICS_DATABASE_URL` — application database; the role needs table-creation rights on first start and read on the source outboxes.
- `SEGMENT_SERVER_WRITE_KEY` — a server source write key; never logged.
- `ANALYTICS_APP_ID`, `ANALYTICS_TENANT_ID` — trusted attribution and the authorized tenant scope (one tenant per process).
- `ANALYTICS_START_AT` — required UTC ISO-8601 launch cutoff; prevents silently loading old purchases into current reports.
- Optional: `ANALYTICS_BATCH_SIZE` (1–500), `ANALYTICS_INTERVAL_MS` (≥1000).

For interaction delivery set `ANALYTICS_CONTEXT_MODULE` to an absolute path of a host ES module exporting `resolveWorld(worldId)` (authoritative world→tenant authorization) and `resolveInteractionIdentity(sourceRecord)` (verified `{userId}` only from trusted identity evidence — never inferred from email, browser data, or the world ID). Without a context module the command delivers billing only and reports the interaction source `disabled`. A partial context module fails startup. Supported interaction records without a resolved identity are `blocked` — no synthetic person IDs are generated — and resume only after a trusted resolver is configured and an operator retries them.

The command owns its connection pool and shuts down gracefully on `SIGTERM`/`SIGINT`. Deploy it as a supervised process; installing the package does not start anything.

## Operator backfill

`node scripts/analytics-backfill.mjs <billing|interaction> <from-ISO> <to-ISO> <tenantId>` replays a bounded (≤24h) `created_at` window of retained records straight to Segment with the same namespaced IDs, so re-runs and connector deliveries deduplicate in the warehouse. Set `ANALYTICS_SOURCE_DATABASE_URL` (read-only credential recommended), `SEGMENT_SERVER_WRITE_KEY`, `ANALYTICS_APP_ID`, and for interaction `ANALYTICS_CONTEXT_MODULE`. Records without verified identity are reported `blocked`, never sent. This is the explicit path for pre-cutoff history and for gaps found by reconciliation; it is an operator action, never an automatic side effect.

## Browser integration

Create a `Registry`, register each `custom.*` event with approved properties and a purpose, and construct `AnalyticsClient` with a `Sink`. The host supplies `collectionAllowed` when regional, account or vendor settings require restrictions. With no policy function, collection is enabled; there is no banner. When collection becomes disallowed the client drops queued observations and rotates identity immediately — on `record`, `identify` or `flush` — rather than waiting for a later flush. Call `reset()` on logout, account switch, suppression or deletion. A pending request cannot be recalled after transmission, and resetting the client does not delete vendor data: the application must perform downstream deletion separately.

Provide an `IdentityStorage` adapter if anonymous identity must persist across reloads. It should use a pseudonymous identifier and clear it on reset. Without one, the ID lasts only for the client instance. Call `identify(verifiedUserId)` after the host has authenticated a user; `identify` cannot itself verify the identity. Anonymous events and the identify call carry the same anonymous ID. Identity linking, upstream consent choices, and deletion propagation must also be configured and verified in each destination. Do not use email addresses as user IDs. Events already sent cannot be relabeled by this client; historical stitching depends on the vendor and its configuration.

The memory queue is bounded; call `flush()` after recording and at appropriate lifecycle points, or use a sink that batches. Failed sends remain pending for retry; closing the page or process loses the queue — observations queued at page exit can be lost — and a batch retried after partial success can be sent again. Stable message IDs support deduplication but do not prove exactly-once delivery. Avoid tracking sensitive fields and unconstrained text, even with custom schemas. Rules with `type: 'string'` require a pattern and maximum length; the host must choose patterns that exclude private content.

## Segment and destinations

`createSegmentSink(transport)` accepts a replaceable transport. `createSegmentHttpTransport({writeKey, timeoutMs?})` implements the Segment HTTP track and identify API using `fetch` with a bounded request timeout; it makes one request per observation and classifies failures (`SegmentDeliveryError`: transient/rate-limited are retryable, other rejections are permanent). HTTP success confirms ingestion acceptance only, not delivery into GA4 or BigQuery. Never embed a server source write key in browser code. Browser apps should supply a wrapper for the official browser SDK and configure its automatic capture and context collection deliberately.

Configure Segment destinations in the Segment account: GA4 for reporting and BigQuery warehouse for the canonical analytical event dataset. Do not also ingest the same observations directly into those destinations. GA4 does not accept the package's dotted event names unchanged: configure destination action mappings using the explicit names in [GA4 mapping](docs/ga4-mapping.md), and confirm identifier/session requirements and supported parameters with the chosen Segment destination. Segment warehouse schema varies by source and configuration; normalize it to the columns in `reconciliation/reconcile.sql`. Do not combine GA4's separate BigQuery export with the Segment feed without source-aware deduplication. Destination setup, delivery, cost, regional settings, deletion and actual schema are unverified in this repository.

## Committed source replay

`readBilling` and `readInteractions` accept an injected read-only PostgreSQL-compatible query interface and a bounded `[from, to)` range on source insertion time (`created_at`); interaction records also return `world_id`, `created_at`, and `occurred_at` for resolver and event-time use. Feed their retained records into `replay` with `mapBillingEvent` or `mapInteractionEvent` and a sink. They never claim or change the business outboxes. Re-read overlapping ranges and compare stable event IDs in BigQuery: neither time-range reads nor Segment ingestion acceptance alone guarantees completeness. Run bounded ranges to control memory and never use a shared synthetic user ID for person-level reports. The billing mapper includes the verified opaque buyer ID when present; interaction events require a trusted resolver for any person identity.

Check source records against BigQuery after the warehouse's expected sync delay. `reconciliation/reconcile.sql` includes a BigQuery fixture and normalized source/destination CTEs; replace those CTEs with authorized snapshots and Segment warehouse views keyed by `portals_source_kind` + `portals_source_id`, and set `late_threshold` to the feed's configured delivery expectation. It reports missing, unexpected, duplicated, mismatched and late records by period. This query was not run against BigQuery. Compare source timestamps in a consistent timezone and re-run overlapping windows for late arrivals. Investigate gaps by source ID, correct the destination or source problem, replay retained records with the same IDs, and reconcile again. Vendor-side deduplication windows and acceptance do not guarantee permanent uniqueness; analytical views must deduplicate by source event ID. Application databases remain the source of truth; Segment acceptance, BigQuery arrival and GA4 reporting are distinct stages.

The inventory in `docs/inventory.json` is a machine-readable audit of implemented surfaces: code presence is marked separately from runtime and vendor verification, marketing/leads and PX distribution are listed as separate excluded pipelines, and unsupported future features are listed outside the catalog.

## Channels configuration

The channels app sends local follow toggles and link-copy attempts/results through its server route when both `NEXT_PUBLIC_CHANNELS_ANALYTICS_ENABLED=true` and `CHANNELS_ANALYTICS_ENABLED=true` are configured, with `CHANNELS_SEGMENT_WRITE_KEY` set to the Segment server-source write key. Nothing is sent by default. This prototype has no authenticated consumer session; follow is local UI state, and a successful copy is not evidence of sharing or delivery. The route accepts only three registered event types and pseudonymous client IDs, and rejects client-supplied authenticated identities. Verify regional collection settings before enabling.

## Production readiness

The channels production build uses the HLS-only `reactor-unavailable` alias because Reactor is an optional peer of the video package; remove this alias and install/configure the SDK before enabling Reactor playback in that app. The current channels application has no authenticated consumer session, and its ingestion endpoint explicitly rejects a supplied user ID. Connecting a real authenticated session requires a trusted server-side identify endpoint and login, logout and account-switch integration; do not accept user IDs asserted by the browser. The current route also needs deployment-level abuse controls and observed request/queue failure monitoring before enabling it publicly. The bounded in-memory queue can lose observations on page termination. Validate the actual Segment-to-GA4 and Segment-to-BigQuery connections, destination mappings, identity behavior, deletion propagation, retention, and reconciliation before claiming production coverage. The fixture demonstrates a query pattern and does not verify the deployed warehouse schema or live data.

## Identity and application attribution

On the server, pass the identity capability's `IdentityProvider` to `identifyVerified(provider, accessToken, anonymousId, sink)`. It verifies the token and active account through `getIdentity` before linking the anonymous ID to the returned user ID. Never pass a typed email or unverified browser user ID. This helper requires an application-owned endpoint protected against cross-site requests and a sink supporting identification; the channels prototype does not yet provide that endpoint or a login flow. Connect logout and account switching to client reset.

For trusted server events, `createSourceIntegration` accepts a mapper, replaceable sink, and host-supplied `tenantId` and `appId`. It sends those identifiers as `portals_tenant_id` and `portals_app_id`; configure the destination mappings and access controls. The host must bind each integration to the correct tenant and application and enforce access itself. The helper performs no durable queuing, transaction integration, scheduling or automatic discovery — use the connector when loss during process termination is unacceptable; do not insert a network call into the billing entitlement dispatcher.

## Reusable app integration

`@portalshq/analytics/channel-events` exports the shared channel action names and `createChannelRegistry`, which accepts the host application's allowlisted channel IDs. `createAnonymousIngestion` in the server entry point validates anonymous observations and delegates delivery to a supplied sink without accepting browser-asserted user identity. `createBrowserRecorder` provides the browser queue, HTTP transport and retry scheduling; the host supplies its endpoint, collection policy and identity storage. The channels app composes these pieces with its own catalog and environment configuration. Applications still need their own authentication, tenant authorization, deployment-level request limits and delivery monitoring.

`createAnonymousIngestion` optionally accepts `resolveContext(request)`. A host can verify its session with the identity capability, authorize tenant and app membership, and return the verified user ID, tenant ID, app ID, and anonymous ID previously bound to that session. The handler rejects mismatched anonymous IDs and client-asserted user IDs before sending. The host must bind the anonymous ID securely during login and implement the resolver; the package cannot establish session or tenant ownership by itself. Channels currently supplies no resolver and remains anonymous.
